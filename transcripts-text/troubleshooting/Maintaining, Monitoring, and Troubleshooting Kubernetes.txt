Introduction to Helm
When you deploy applications to Kubernetes, you're managing multiple
manifests. These are often huge metadata files that contain all the details of your
application's deployments, services, and configuration. But managing raw YAML
manifests quickly becomes a challenge. You're juggling dozens of files, copying
and pasting configurations, and making the same change in 10 different
places. This is where Helm comes in. Helm is the package manager for
Kubernetes. Think of it like apt for Ubuntu or Homebrew for macOS but made
especially for Kubernetes applications. Helm helps you define, install, and
upgrade even the most complex Kubernetes applications. It's a graduated project
in the Cloud Native Computing Foundation maintained by over 400 developers
and backed by companies like Google, Microsoft, and Red Hat. It's the industry
standard for managing Kubernetes applications. Here's the problem Helm
solves. Without Helm, you're managing individual YAML files. Changing any
values in those YAML files is difficult, as the value has often been used across
multiple different files. With Helm, you package everything into a chart, one
cohesive unit. Now you can make whatever changes you need to in one single
place, and Helm updates it across all of your YAML files. Another benefit of this is
that you can now easily upgrade or roll back a release with a single command. You
just need to give the helm upgrade command, and Helm updates all of your
YAML files and deploys the new version of your app. These versions of your
application are also tracked in Helm, like you would with Git. Let's break down
what a Helm chart actually looks like. Every chart follows the same
structure, which makes them easy to understand once you've seen a few. First,
Chart.yaml. This is the metadata file. It describes what the chart is, what version it
is, and who maintains it. This Chart.yaml file is required for every Helm chart. Next,
we have one or more values.yaml files. These files contain all of your configuration
values, so that's image tags, replica counts, resource limits. Everything that might
change between environments goes in here. Finally, the templates directory. This
is where your Kubernetes manifests live, but they're not plain YAML anymore.
They're Go templates. Helm takes the values from these values.yaml files and
injects them into these templates to generate the final Kubernetes
manifests. Installing Helm is straightforward. On macOS, it's a simple Homebrew
install. On Linux, there's an official install script. Windows users can use
Chocolatey or download the binary directly. Now that you understand what Helm
is and how charts work, let's see it in action. In the next clip, we'll deploy our
guestbook application using Helm and see these concepts come to life.

Kubernetes High Availability Features
When you deploy applications to Kubernetes in production, uptime isn't
optional. It's expected. Your applications need to stay online during routine
maintenance, node failures, and cluster upgrades. This is where high availability
features come in. Kubernetes provides three core mechanisms that work
together to keep your applications running even when things go wrong. Let's
explore each one. The first mechanism is replicas. In the previous demo, we
deployed our application with multiple frontend and backend pods. You saw how
we could scale those numbers up and down with a simple helm upgrade. But why
did we run multiple copies in the first place? The answer is redundancy. Those
replicas all serve the same traffic, sitting behind a Kubernetes service that load
balances requests across them. Now if one or more pods crashes, maybe due to a
bug or maybe due to memory pressure, the other replicas keep serving
traffic. Your users don't notice anything. The application stays online. But running
multiple replicas isn't enough. During maintenance operations, as you're going to
see shortly, you need to make sure Kubernetes doesn't accidentally disrupt all
your pods at once. That's where pod distribution budgets come in. A pod
distribution budget, or PDP, is a Kubernetes resource that defines how many
pods must remain available during voluntary disruptions. Voluntary disruptions
are things you control, draining a node for maintenance, upgrading the cluster, or
scaling down a deployment. A PDP acts as a safety constraint that tells
Kubernetes no matter what, you must keep this minimum number of pods
running. Let's visualize exactly how a pod distribution budget protects your
application during maintenance. Our application has a total of four pods running
across node A and node B. We've defined a PDP rule that tells Kubernetes you
must always keep at least three pods available. Now, imagine we need to patch
the OS on node A, so we run a node drain command. Without a PDP, the drain
command would attempt to evict both pods from node A immediately, which
would leave just the two remaining on node B. Because of the pod distribution
budget, the eviction API rejects the request to eliminate both pods, and only one
is evicted. A new pod then gets created on node B, replacing the one that was
destroyed on node A. Once the new pod on node B has started successfully, the
other remaining pod on node A can then be destroyed. Since node A is now
cordoned off, a fourth pod gets created on node B, bringing us back to our total
deployment request of four pods. The PDP ensured that the minimum number of
free available pods was never breached. The third piece of high availability is pod
anti-affinity. This controls how Kubernetes spreads your pods across the cluster
nodes. Without anti-affinity rules, Kubernetes might schedule all your pods on
the same node. If that one node fails, your entire application goes down. Pod
anti-affinity lets you tell Kubernetes prefer to spread these pods across different
nodes. With anti-affinity configured, your pods are distributed evenly, two on
each of your three worker nodes. Now if one node fails, you only lose a third of
your capacity. The remaining pods on the other nodes continue serving
traffic. This is especially valuable during cluster maintenance. When you upgrade
a node and reboot it, only the pods on that specific node are affected. The pods
on other nodes keep your application running. These three features work
together to create true high availability. Replicas give you redundancy, multiple
pods handling the same workload. Pod disruption budgets protect you during
maintenance, ensuring Kubernetes never disrupts too many pods at once.
And pod anti-affinity distributes your risk, spreading pods across multiple nodes
so that no single failure takes down your entire application. Together, these
features enable zero downtime cluster upgrades, safe node maintenance, and
resilience against failures.

Preparing for a Kubernetes Cluster Upgrade
Kubernetes releases new versions every few months, which means cluster
upgrades are a regular part of maintaining a production environment. But how do
you safely upgrade a cluster whilst keeping all the production applications
running on it online? Let's walk through how to plan a safe, zero-downtime
cluster upgrade. Kubernetes cluster upgrades normally follow the same
order. Control plane first, then worker nodes one at a time. Why this
order? Well, the control plane components need to be upgraded before the
worker nodes because they're designed to support worker nodes at older
versions. So the sequence is upgrade the control plane, then upgrade worker 1,
then worker 2, and so on. Upgrade one worker node at a time, never all at
once. Let's walk through the pre-upgrade checks that a Kubernetes administrator
will always follow. First, verify cluster health. Check that all nodes are ready, all
kube-system pods are running, and there are no resource exhaustion
warnings. Second, back up the Kubernetes database. The etcd database stores
all your cluster states, every deployment, every service, every config map. If
something goes wrong during the upgrade, this backup is your safety net. Finally,
review the Kubernetes release notes. Look for braking changes or depreciated
APIs that might affect your workloads. Before you touch a production cluster, you
need a written maintenance plan. A good maintenance plan should document
the entire upgrade sequence. This will include the exact commands you'll
run, verification steps at each phase, success criteria, and most importantly, your
rollback procedures. Beyond the technical details, there are other things to
include as well. Stakeholder communication. Who needs to know about this
maintenance window? Timeline and milestones. How long will each phase
take? Risk assessment. What could go wrong and how will you handle it?
Contact information for escalation if something does go wrong. Now, with the
proper high availability features configured that we discussed previously, your
applications should experience zero downtime during a cluster upgrade. As you
upgrade worker nodes one by one, pods get rescheduled to other nodes. Because
you have multiple replicas spread across nodes, your application stays online
throughout the process. Now let's talk about what happens if something goes
wrong. What if a worker node upgrade fails? You have two main options. Option 1,
fix and retry. If the upgrade fails due to a transient issue, maybe a network
timeout, or a temporary resource constraint, you can troubleshoot the issue and
retry the upgrade on that node. Option 2, replace the node. This is often the safer
choice, especially in cloud environments like AWS. The key question is, when do
you continue versus when do you abort? If one worker node fails but you can
replace it, continue with the upgrade. But if the control plane fails, it's normally
better to stop immediately. Just don't upgrade worker nodes until the control
plane is stable.

Kubernetes Observability
You can't improve what you can't measure. If you're running a production cluster
without observability, you're flying blind. That's not acceptable. So let's talk about
observability. When discussing observability, there are three main pillars we're
concerned with. Firstly, metrics. These are numerical measurements over
time, things like CPU usage, memory consumption, request rates, error rates. Next,
logs. These are timestamped records of discrete events. Think application logs,
error messages, and audit trails. Logs tell you what's happened and provide
context for when you're troubleshooting issues. Finally, traces. These show the
path of a request as it flows through your distributed system. In this module,
we're going to focus on the first two, metrics and logs. These are the foundations
of Kubernetes observability and where you'll get the most value for your effort. So
why invest time and resources in observability? Four reasons. First, you can
detect issues before your users complain. If you see memory usage climbing
steadily, you can act before pods start getting killed. Second, you understand
system behavior under load. When traffic increases, what happens to your CPU
usage? What happens to response times? Third, you make informed decisions
about scaling and upgrades. Should you add more nodes? Do you need to
increase pod replicas? Which pods are consuming the most resources? Fourth,
you prove reliability to stakeholders. When someone asks, how reliable is our
application, you need data, not guesses. Metrics like uptime percentage, error
rates, and response times let you answer with confidence. In this module, we're
going to build observability from the ground up. We'll start simple with the
Kubernetes metrics server. This gives you basic resource metrics, but has serious
limitations. Then we'll move to production-grade tools, Prometheus for metrics,
Loki for logs, and Grafana for visualizing everything. Finally, we'll use that data to
track reliability with service-level objectives. This is where observability translates
into business value.

Introduction to Prometheus and Grafana
For production Kubernetes environments, you need more than basic metrics. You
need historical data, custom metrics, powerful querying, and visualization. That's
where Prometheus and Grafana come in. These are the industry standard tools
for Kubernetes observability. Let's look at what each one does. Prometheus is an
open-source monitoring and alerting toolkit built specifically for metrics. At its
core, it's a time series database that stores numerical data points over time. For
example, CPU usage and memory usage. The great thing about Prometheus is
that it scrapes metrics from your cluster and applications automatically. You don't
have to push data to it. Prometheus also gives PromQL, the Prometheus Query
Language, which lets you analyze your metrics in sophisticated ways. Finally,
Prometheus has built-in alerting. You define rules like alert me if CPU usage
exceeds 80% for 5 minutes, and Prometheus monitors these conditions and
fires alerts when thresholds are breached. While Prometheus stores and queries
metrics, Grafana visualizes them. Grafana is an open-source visualization and
analytics platform that connects to multiple data sources like Prometheus and
turns that data into dashboards with graphs, gauges, and tables. The Grafana
community maintains hundreds of pre-built dashboards that you can import. They
show things like cluster health, node resources, and pod statistics. You can also
create custom dashboards for your applications. For example, to track your API
request rates or your database query latency. Grafana can also combine data
from multiple sources into a single dashboard. You might have Prometheus for
your Kubernetes metrics, your cloud provider's monitoring service for
infrastructure metrics, and your application database for business metrics, all
visualized together. With Prometheus and Grafana, you can monitor metrics at
four different levels. Cluster-level metrics show overall cluster health. This is
things like total CPU usage across all nodes, total memory consumption, and
network throughput. Node-level metrics show individual server resources. That's
things like per-node CPU usage, per-node memory, and disk utilization. This helps
you identify hotspots, i.e., which nodes are overloaded. Pod-level metrics show
container resources. So that's things like per-pod CPU, memory usage, restart
counts, and container states. This helps you identify which workloads
are resource-hungry and which pods are unstable. Finally, application-level
metrics are custom metrics from your application, things like HTTP request
rates, error rates, and database query counts. This is where observability
connects to business value. Prometheus and Grafana together give you
production-grade observability. Let's get them installed on our Kubernetes
cluster next.

Centralized Logging in Kubernetes
Metrics tell you what is happening in your system, but they don't tell you
why. That's where logs come in. Every application produces logs. But in
Kubernetes, accessing and using those logs effectively is more challenging than
you might expect. The basic way to view logs in Kubernetes is kubectl logs. But
this approach has serious limitations in production. First, you can only view logs
from one pod at a time. If you have 10 pods and you're troubleshooting an
intermittent issue, you're running kubectl logs 10 times. Second, logs are lost
when pods restart or crash. If a pod crashes due to an error, the logs that will tell
you why often disappear with the pod. Third, there's no way to search across
multiple pods. You can't ask, show me all the error logs from any backend pod in
the last hour. You have to check each pod individually. Fourth, there's no
retention. They exist only as long as the pod exists. And even then, they're
rotated and discarded to save disk space. Finally, there's no way to correlate logs
with metrics. When you see a metric spike in Grafana, you can't easily jump to the
relevant logs to see what was happening at that exact moment. The solution is
centralized logging with Loki and Grafana Alloy. Loki is a log aggregation
system. It collects logs from your entire cluster and stores them in a central
location with retention. You can search across all logs, filter by pod or namespace
or log level, and keep logs for days or weeks. Grafana Alloy is a daemon set that
runs on every node in your cluster. It collects logs from all containers on that
node and ships them to Loki. Right now, our application uses basic print
statements that output plain text. We're going to upgrade that to structured
logging using JSON format with fields like timestamp, log level, event type, and
custom data. This makes logs much easier to query. For example, you can filter to
show only error-level logs. You'll also be able to extract specific values from the
log fields. Centralized logging with Loki and Grafana Alloy solves the limitation of
kubectl logs. You get persistent storage, cross-pod searching, powerful querying
with LogQL, and integration with your metrics dashboard. Let's see it in action
next.

Service Level Indicators and Objectives
We've talked about collecting metrics and logs. We've built dashboards that
visualize that data. But how do you know if your system is actually reliable? I
mean, how do you measure success? This is where service level indicators,
service level objectives, and service level agreements come in. Let's break down
what each of these means. A service level indicator, or SLI, is a specific metric
that measures one aspect of your service's reliability. There are three common
types of SLIs. Availability measures the percentage of time your system
is reachable and ready to serve traffic. It's calculated as uptime divided by total
time. Latency measures response time, typically as a percentile. P95 latency
means 95% of requests are faster than this threshold. Error rate measures the
percentage of requests that fail. It's calculated as errors divided by total
requests. A service level objective, or SLO, is your target for an SLI. It's the
internal goal your team commits to. For example, your availability SLO might be
99.5% uptime. Your latency SLO might be P95, less than 200 ms. Your error rate
SLO might be less. 0.5% errors. These are all internal commitments. They are
targets that guide your operational decisions and help you prioritize reliability
work. SLOs are not aspirational goals like be as fast as possible. They're specific,
measurable targets with numbers attached. A service level agreement, or SLA,
takes an SLO and adds consequences. It's a contract with your customers. For
example, we guarantee 99.5% uptime. And if we violate that, you get a 10%
service credit. That's an SLA. It's more formal and legally binding than an SLO. Not
every SLO needs to be an SLA. You might have internal SLOs that are stricter
than your external SLAs. For example, you might target 99.9% internally, so you
have buffer room before violating your 99.5% SLA with customers. Now there's
one concept that brings this together, error budgets. If your availability SLO is
99.5%, that means you have a 0.5% budget for failures. When your error budget is
low, for example, when you've used up most of your allowed downtime, then
that's when you'll typically take action. You'd probably focus more on reliability
for a while or slow down deployments to production. Error budgets help you
balance velocity and reliability. They give you a data-driven way to make
decisions about risk.

Kubernetes Troubleshooting Workflow
Things break in Kubernetes. Pods crash, images won't pull, and services can't
connect. This is all perfectly normal. The difference between a good Kubernetes
operator and a struggling one isn't where the problems happen; it's how quickly
and systematically you can diagnose and fix these issues. So in this module, we're
going to work through five common Kubernetes issues you'll encounter in
production. First, CrashLoopBackOff, when pods keep starting and crashing
repeatedly. Second, ImagePullBackOff, when Kubernetes can't pull your
container image. Third, pending pods, when pods are stuck and won't schedule
onto nodes. Fourth, networking issues, when services exist but can't
communicate. Fifth, OutOfMemoryKilled, when containers exceed their memory
limits and get terminated. Each of these has different symptoms and different
root causes, but we'll be using the same troubleshooting workflow for all of
them. Here's the workflow you'll follow for every issue. Step 1, observe. Run
kubectl get pods. What's the symptom? Which pods are affected? Step 2,
describe. Run kubectl describe pod. Get the detailed status and event
history. Step 3, logs. Run kubectl logs. Check what the application is actually
reporting. Step 4, events. Check cluster events or specific resources. Look for
error messages from Kubernetes itself. Step 5, fix. Make the change. Update your
configuration, fix your manifest, and adjust your resources. Step 6, verify. Confirm
the fix worked. Pods should be running and the application should be
healthy. This workflow becomes second nature with practice. The key is staying
calm, being systematic, and letting kubectl guide you to the problem. Let's start
troubleshooting. First up, CrashLoopBackOff, one of the most common pod errors
you'll see in Kubernetes.
