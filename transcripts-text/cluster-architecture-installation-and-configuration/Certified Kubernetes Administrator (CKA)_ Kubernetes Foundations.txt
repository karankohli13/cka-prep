find each other by name. The cluster DNS service for all service discovery, yeah,
that's CoreDNS. It runs as a deployment in the kube system namespace,

service IP for its DNS. Speaking of which, every service gets a DNS name, service-

Services and the selector-label contract
Our next learning objective is how services expose workloads to the network. Now
Pods are ephemeral by design. Their IP addresses change. They come and go
constantly. A service sits in front of a set of Pods and provides a stable virtual IP
and a stable DNS name. The service is how clients, whether other Pods or
external users, actually find your application in a world where the back end is
always moving. This slide shows the contract between a service and its back-end
Pods. The service stays stable while labels in readiness determine which Pod IPs
are actually eligible to receive traffic. The service provides a stable virtual IP, or
VIP, for a set of Pods. That virtual IP, usually a cluster IP inside the cluster, is the
front door your clients call. Meanwhile, the back-end Pods can come and go
freely behind it. Pods appear in endpoint slices when labels match. Kubernete's
doesn't send traffic to a Pod just because it exists. The Pod's IP address only
shows up in an endpoint slice when the Pod matches the service's selector. Now
endpoint slices are the modern replacement for the legacy Endpoints
object. They're the scalable back-end inventory for a service. And on the exam,
this is the first object you check when service routing looks wrong. The service
selects Pods by matching their labels. That's the key contract. Label matching is
the only way a Pod becomes a candidate for traffic. No matching label, no back-
end membership, full stop. If a Pod loses its label or fails readiness, its IP is
removed from the list. Membership is conditional in Kubernetes. If the Pod stops
matching the selector or if it fails its readiness probe, Kubernetes pulls its IP out
of the back-end list automatically. And lastly, if labels match and readiness
passes, Pod IPs are included in endpoint slices. So the full rule is simple, labels
qualify the Pod, and readiness authorizes traffic. Both have to be true before a
Pod IP appears in an endpoint slice. This is the full request path that every client-
to-Pod connection follows. And understanding that is essential for
troubleshooting. The path has three hops. First, the client does a DNS lookup for
the service name, and core DNS returns the service's cluster IP. Second, the
traffic goes to that cluster IP, and kube proxy, which has programmed IP tables or
IPVS rules on every node, translates the cluster IP to a back-end Pod IP. Third, the
traffic arrives at the Pod. Four components are involved in making that work, core
DNS, the service object, kube proxy, and the Pod itself. If any one of them is
broken, the connection fails.
Three service types
We have three service types, and they're layered on top of each other. A
LoadBalancer includes a NodePort, which includes a ClusterIP. ClusterIP is the
default, and it's internal only. It provides a virtual IP for service-to-service
traffic that's reachable only from inside the cluster. Your laptop can't ping it, but
other Pods can. ClusterIP gives you a stable endpoint for Pods selected by
labels. Clients always hit the same IP, and the service fans out to whichever Pods
currently match the selector. This is the standard pattern for app to database
or front end to back-end traffic. Core DNS auto creates a DNS record for every
service in the form service-name.namespace.svc.cluster.local. Same namespace
Pods can use the short name, but cross-namespace access needs the fully
qualified domain name. Now NodePort extends ClusterIP by adding an external
entry point. It opens the same high port, somewhere between 30,000 and 32,767
on every node in the cluster. Traffic hitting a node IP on that port routes through
the service and onto the Pods. NodePort is accessible from outside the
cluster, assuming your node IPs are routable. This is the exam-friendly way to hit
a service from outside, and it works in local clusters like kind and minikube. In
kind, the extra port mappings from our previous module map to the NodePort on
your host. LoadBalancer extends NodePort by adding a cloud provider
LoadBalancer in front. In AWS, Azure or GCP, Kubernetes automatically provisions
a real external LoadBalancer with the public IP. Clients hit the LoadBalancer, and
it distributes traffic to NodePort on each node. The LoadBalancer also health
checks the nodes and removes unhealthy ones from rotation automatically. On
kind, however, LoadBalancer services stay pending forever because there is no
cloud provider. That's expected behavior, not a bug. You can't verify service
connectivity from your laptop because ClusterIPs are only routable from inside
the cluster. Every test has to originate from inside a Pod. Every service gets a
DNS record automatically, as I mentioned, in the form
servicename.namespace.svc.cluster.local. Core DNS watches the service objects
and creates the records for you, so there's no manual DNS config for you to worry
about. Same-namespace Pods can use the short name. If you're in the same
namespace as the service, just my-service resolves correctly, which can save you
a lot of typing. This works because every Pod's /etc/resolv.conf lists search
domains, including your namespace.svc.cluster.local and cluster.local, and the
short name gets expanded against those. Now cross-namespace access is
different. From namespace A, calling a service in namespace B requires the fully
qualified domain name. All of this testing has to run from inside a Pod, not from
your host. Your host sits outside the cluster network. The command pattern here
is kubectl run debug with the BusyBox image, the --rm and -it flags and --nslookup
my-service. That spawns a throwaway Pod, runs the DNS lookup, and cleans itself
up on exit. Swap nslookup for wget, and you go beyond DNS resolution and test
end-to-end connectivity, confirming that DNS resolved, the ClusterIP responded,
and a Pod back end actually answered.
Namespaces, labels, and annotations
Our next learning objective is organizing resources at scale. Let's get the precise
definitions down here because these distinctions matter for the exam and for
your production operations. Namespaces scope resource names and enable
RBAC policies. A namespace is a Kubernetes object that partitions the
cluster. Resources with the same name can coexist in different namespaces
without conflict. RBAC roles are bound at the namespace level, and that's how
you grant a team access to just their piece of the cluster. Labels are for
selection. A label is a key value pair in metadata.labels. Services select Pods by

label. Labels are the wiring that connects objects to each other. Annotations, on
the other hand, carry metadata but do not affect scheduling or routing. An
annotation stores arbitrary data, things like build, commit SHAs, change tickets or
owner emails. Kubernetes controllers ignore annotations entirely. They're for
humans and for external tooling, nothing more. For querying, kubectl get pods
with the -A flag spans all namespaces. This is useful when you can't remember
which namespace a Pod lives in. For filtering, compound selectors like the kubectl

parentheses. The -l flag uses the full label selector syntax. Our fourth and final
learning objective in this module and the single most valuable skill in this entire
course is the diagnostic ladder. Four commands executed in order answer every
what's broken question you'll ever face in Kubernetes. Get tells you the current
status, describe tells you why the status exists, logs tells you what the application
itself said, and events tell you what the cluster as a whole did. Four rungs, each
one revealing a deeper layer than the last. You start at the top and work down
until you find the root cause. Rung 1 is get. Kubectl get pods shows you status,
ready, restarts, and age. If the status is anything other than running, that's your

Digging into the diagnostic ladder
Troubleshooting makes up 30% of your CKA score. To master it, you need a
repeatable system. We'll use the diagnostic ladder, and rung 1 is kubectl get. In
this segment, I'm deliberately breaking a Pod by using an --image tag that doesn't
exist. NGINX does not exist. After giving the kubelet a few seconds to attempt the
pull, I run a simple get pods. Look at the STATUS column. This is your first and
most vital clue. You see ErrImagePull. This tells you exactly where the failure is
occurring. The container runtime can't find the image. If you wait a few more
seconds, this will flip to ImagePullBackOff. This means Kubernetes has tried,
failed, and is now waiting in an exponential backoff period before trying
again. Notice that READY is 0/1. The API object for the Pod exists, but the
container inside it was never created, a common mistake on the exams to jump
straight into complex YAML debugging. Don't do that. Always start at rung 1. Read
the status, identify the failure category, and then and only then are you ready to
climb to rung 2. We've climbed to rung 2 of the diagnostic ladder. If kubectl get
gives you the what, kubectl describe gives you the why. On the CKA exam, you
don't have time to scroll through 80 lines of YAML. You've got to head straight to
the event section at the bottom. Think of the events as the cluster's narrative. It's
a chronological diary of the Pod's life. Looking at the filtered output, we see the
story unfold. First, Normal Scheduled. The scheduler did its job and placed the
Pod on worker node 2. Then Normal Pulling. The kubelet tried to fetch our image,
and then there it is, the smoking gun, a Warning Failed message explicitly stating
NotFound for NGINX does not exist. Pay close attention to the State and
LastState fields in the container spec. Right now, the state is waiting because of
that back off. In a real-world scenario where a Pod's crashing repeatedly, the
LastState field is pure gold. It'll show you the exit code of the previous process.
For the CKA, if you see ImagePullBackOff in the status, your first move should
always be a describe to verify the image name, the registry path, and the pull
secrets. We've reached the top of the diagnostic ladder. Rung 3 is kubectl logs. In
this case, look at the error container is waiting to start. That's a massive clue.
Because the container never actually ran, there are no application logs to read.
On the exam, if you get this error, you stop looking at the app code and go back
to the infrastructure. It's an image secret or resource issue. However, keep this in
your back pocket. If a Pod is in CrashLoopBackOff, it means the container did
start but then died. In that scenario, you've got to use kubectl logs --
previous. That flag's the only way to hear the final words of the dead container to
see if it threw a Java stack trace or a segmentation fault before it collapsed. Rung
4 is the cluster-wide event stream. While describe shows events for a specific
object, kubectl get events lets you see the narrative across the whole
namespace. I've used a field selector here to filter only for our broken Pod and
sorted them by time. Notice the LAST SEEN and REASON columns. This confirms
the timeline we saw in DESCRIBE, but in a clean tabular format. If you can't find
the smoking gun in the logs, the event stream will tell you if the kublet's
struggling, if the node is out of disk space or if the OOM killer is stalking your
processes. Master this four-step rhythm, get, describe, logs, events.
