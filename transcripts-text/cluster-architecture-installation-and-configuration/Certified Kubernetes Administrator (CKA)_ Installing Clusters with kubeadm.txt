Kernel modules and sysctl: the networking foundation
Why does kubeadm require specifi kernel modules and sysctl parameters? Two
kernel modules and three sysctl parameters form the networking foundation of
every kubeadm cluster. Getting any of them wrong means kubeadm either fails
fast or your cluster breaks later in ways that are much harder to diagnose. The
overlay kernel module enables the overlay fs filesystem, which is what containerd
uses to stack read-only image layers under a writeable container layer. This is the
same layered-image idea used by Windows containers under the hood. Without
overlay, loaded containerd can't start containers. The br_netfilter module wires
Linux bridged traffic, meaning packets crossing a software Layer 2 switch into
iptables and netfilter, which is the Linux packet filtering subsystem that acts like
a host firewall and is what kube proxy and most CNI plug-ins use to enforce
service rules across pods. This sysctl turns the host into a Layer 3
packet forwarder between network interfaces. This is required because pods on
different nodes depend on the host kernel to route traffic between them. This
sysctl makes bridged Layer 2 traffic visible to iptables, which the official kubeadm
documentation lists as a hard requirement for cluster networking to
function. Persistence is what keeps these settings in place across reboots, since
modules loaded with mod probe and sysctl set with sysctw both evaporate when
the node restarts. Drop your module names into etc/module-load.d/k8s.conf and
your three sysctl values into etc/sysctld/k8s.conf. Then runs sysctl system, so
systemd, the Linuxer controller, analogous to Windows Service Control
Manager, applies them at every boot. Oh, it's a mouthful, huh? The Windows
analog to this is auto loading a driver at startup via the Registry under
HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services name start=2. The
cruel part of this configuration and these requirements is that misconfigs are
silent, and this is also because kubeadm pre-flight checks can pass, and your
pods will happily get IP addresses, but cross-node pod traffic times out without
an obvious error message. On the CKA exam, the punishment is not the fix
itself, but the minutes you burn troubleshooting routing, and CNI before you
remember to verify ls mode in sysctl on every node.
kubeadm prerequisites: what must be correct before init
Before kubecdm initializes a cluster, it assumes the host's already correctly
configured, and these four conditions are what kubecdm preflight verifies on
every node. First, swap has to be disabled. Swap is the Linux equivalent of the
Windows page file, and the kubelet refuses to run with swap enabled because
the scheduler relies on accurate memory accounting. So you disable swap with
swapoff and remove the swap entry from etc/fstab, the file system mount table,
so it doesn't return after a reboot. The bootstrap worker assumes every node runs
the same minor version of all three binaries, and version skew between the
control plane and worker nodes causes the join to fail. Kernel modules and sysctl
have to be configured as a networking foundation. Well, sure, this is the work from
the previous slide, and it has to be in place before a kubeadm init runs
because pre-flight refuses to continue without it. Lastly, kubeadm is a
bootstrapper, not an installer. So if you install a CRI-compliant runtime such
as containerd before a init and a CNI plug-in, by the way, if you don't remember,
CNI stands for Container Network Interface, the pluggable component that
provides pod networking, such as calico or flannel after a init. This is the verbatim
shell sequence that loads the two required kernel modules, persists them across

expects. Modprobe is the Linux command that loads a kernel module into the

1.24. This infographic shows the relationship between the kubelet, the Container
Runtime Interface socket, and the container runtime itself. The kubelet is the
node agent that runs every pod, CRI is the standard contract between kubelet

What kubeadm init creates
What does kubeadm init actually create under the hood? Kubeadm init does six
things in sequence, and you need to recognize each artifact on disk
to troubleshoot a failed bootstrap during the exam. Kubeadm generates its own
certificate authority, or CA, on first run, and that CA's private key signs every
other certificate in the cluster. Losing /etc/kubernetes/pki key means rebuilding
the cluster rather than rotating credentials. A static pod is one the kubelet runs
directly from a YAML file on disk with no scheduler involved. Kubeadm drops four
manifests here for kube API server, etc.d kube controller manager, and kube
scheduler. Admin.conf is the cluster's root kube config at etc/kubernetes/
admin.conf with root-only permissions until you copy it to your system's home
directory. This is why kubectl returns connection refused before the copy
step. Kubeadm issues a separate client and server certificate for each control
plane component, plus the kubelet's own client certificate, so PKI ends up with
around 15 pem files, all signed by the CA from step one. The kubelet's pod
manifest path flag points at etc/kubernetes manifests, so the moment kubeadm
writes those four YAML files, the kubelet picks them up and starts the control
plane. That's how Kubernetes bootstraps itself without a scheduler to schedule
its own scheduler, if that makes sense. Kubeadm prints a complete join command
at the end of a init, including a short-lived bootstrap token and the SHA256 hash
of the CA certificate. Save that line or regenerate it with kubeadm token create
print join command. Bootstrapping a production Kubernetes cluster requires
a predictable multi-stage lifecycle that kubeadm init executes through a series of
discrete phases. For the pre-flight phase, the tool validates the host environment
to ensure that swap is disabled, ports are open, and the CRI is fully functional. For
the certs phase, kubeadm generates a complete X509 cryptographic identity and
public key infrastructure required for secure communication across the
cluster. Now let me state parenthetically that Kubernetes does that for security
and convenience, but many businesses then swap in their own internal PKI. For
the kubeconfig phase, the system writes the necessary config files containing the
credentials required for the cluster components and the administrative user to
authentic to the API server. For the kubelet start phase, the utility writes the
environment file and starts the node agent so it immediately begins hosting
cluster services. For the control plane phase, the engine creates the static pod
manifests that instruct the local kubelet to automatically spin up the API
server, controller manager, and scheduler. For the etcd phase, the process
initializes the local, single node database instance as a static pod to serve as the
cluster's distributed data store. For the upload-config phase, the controller saves
the installation parameters into a config map within the cluster to streamline
future maintenance and updates. For the bootstrap-token phase, the framework
creates the cryptographic tokens and generates the exact join command
required to securely attach worker nodes. Mastering these individual phases is
critical for debugging initialization failures and navigating complex cluster
lifecycle tasks in production and on your exam.

plug-in is the component the kubelet invokes whenever a pod's scheduled. And
the plug-in's job is to allocate a pod IP from the cluster's pod CIDR block,
Common Internet Domain Routing. We're thus configuring the host routes that
let that pod reach others, and this is the entire reason every node reports
NotReady after kubeadm init. The kubelet's readiness checklist includes, can I
assign Pod IPs? And the answer is no until a CNI binary exists on the node, which
is why the not ready condition shows network plug-in NotReady as its specific
reason. CoreDNS is the cluster's internal DNS server, and this is roughly
comparable in role to a Windows DNS server inside an Active Directory site. And it
runs as a deployment that needs Pod IPs to start, no CNI, no Pod IPs, no
CoreDNS, no service discovery. A DaemonSet is a Kubernetes workload type that
runs exactly one pod on every node in the cluster. Think of it as a per-node agent,
the way a Windows service installed on every domain-joined machine is a per-
host agent. This is the correct shape for a CNI implementation because every
node needs its own networking agent. In sum, Kubernetes delegates networking
to plug-ins, as we've seen with CNI defining the interface. Kubernetes
intentionally doesn't ship with a built-in CNI because the platform owns
scheduling and lifecycle, and the network is the plug-in's job. Three popular CNI
choices, and for CKA prep, you want the one that gives you clean networking
basics, plus network policy coverage, and that's Calico. Calico supports network
policy, is common in self-managed clusters, and is therefore a strong default for
our CKA practice. Calico implements the network policy API, which the CKA exam
tests in the services and networking domain, and as I said, is the most widely
deployed CNI in self-managed production clusters. The default CIDR is
192.168.0.0/16, the install is documented by the Tigera operator via Helm, and the
project is actively maintained. Flannel is lightweight and simple, good for basic
pod networking, but it has no network policy. So, Flannel is the simplest CNI to
install, and it runs cleanly on small clusters. But because it doesn't implement
network policy, it can't answer half of the services in networking domain that we
need to understand and use on the exam. So therefore, Flannel is useful to
recognize on the exam by name, but it's not the right choice for our prep.
Cilium gives us advanced eBPF networking, strong visibility and policy
features, but is more complex than what most CKA candidates need. Specifically,
Cilium is the modern frontier CNI built on eBPF, and eBPF is a Linux kernel
technology that runs sandboxed programs inside the kernel, comparable in spirit
to the Windows filtering platform, but more general. And it ships excellent
observability and policy, however, it's overkill for CKA practice. You should know it
exists though, because exam questions sometimes will name check it. So in
summary, our trade is simple. Calico presents the right balance of real production
tool and stable on a three-node lab. And every later course in this Pluralsight site
